# FOSS alert lifecycle / durable execution fit

**Historical research:** this assessment preceded the contract interview. The confirmed [backend architecture](../architecture/backend.md) permits up to three transient-failure repeats per paid step with durable accounting; references below to a no-automatic-retry requirement describe the earlier constraint. The conclusion about external side-effect uncertainty still applies.

## Executive assessment

No shortlisted product replaces Varde's complete lifecycle: immutable alert intake, versioned generated views, durable history, deduplication policy, Android sync recovery, and provider-neutral decision/LLM validation. **ntfy and Gotify are push/message transports with finite product-specific message semantics, not an alert-domain system.** DBOS is closer to reusable durable processing, but adds a runtime/service database and still leaves alert identity, retention policy, generated-view versioning, idempotency, UI/sync APIs, and validation to Varde. A practical fit is to keep canonical records and lifecycle in Varde's SQLite database, optionally use a transport for best-effort push, and consider DBOS only if workflow orchestration proves substantial enough to justify an additional runtime/database dependency.

This assessment treats the stated requirements as the target, not as verified decisions. No code or credentials were inspected.

### Evidence versus inference and uncertainty

- **Evidence:** ntfy documents a default 12-hour cache and configurable cache duration/storage; cached history can be replayed, and publish options include sequence identifiers. Its docs describe those sequence features as notification update/clear/delete operations, not a general dedupe contract. Sources: [ntfy config](https://docs.ntfy.sh/config/), [publish](https://docs.ntfy.sh/publish/).
- **Evidence:** Gotify configuration documents SQLite; server repository owns its MIT license. The retention issue is a feature request. Sources: [config](https://gotify.net/docs/config), [repository](https://github.com/gotify/server), [retention issue](https://github.com/gotify/server/issues/376).
- **Evidence:** DBOS documents restart recovery from last completed step, at-least-once step execution, and no re-execution after completed steps; configurable step retries are available. Sources: [workflow tutorial](https://docs.dbos.dev/python/tutorials/workflow-tutorial), [step tutorial](https://docs.dbos.dev/python/tutorials/step-tutorial).
- **Inference:** Using ntfy/Gotify as authoritative alert storage would couple Varde's domain history and sync semantics to transport-specific retention and message APIs. This inference follows from the requested indefinite/versioned archive and the documented transport cache/message features; neither product claims to provide that Varde domain contract.
- **Uncertainty:** This is a documentation-level shortlist, not a runtime test. Exact behavior under disk-full conditions, database corruption, upgrades, retention edge cases, and client reconnect races was not validated. Gotify's absence of documented retention is not proof that no retention behavior exists in every version. DBOS's exact minimal container/process topology and supported SQLite operational envelope should be verified against the selected version before adopting it.

## Architectural consequences

1. **Keep Varde as system of record.** Store every accepted original alert immutably and associate generated rich views as append-only/versioned records (including generator/model/version metadata and validation outcome). Define duplicate identity and collision behavior explicitly; do not rely on transport sequence IDs or workflow idempotency as the product's dedupe policy.
2. **Treat notifications as lossy hints.** Push should contain a stable alert identifier (and perhaps a view revision), while Android performs authenticated sync against Varde after push, reconnect, app launch, and periodic recovery. This remains necessary regardless of ntfy/Gotify because push delivery is best effort and transport message history is not the app's canonical sync cursor.
3. **Constrain external-call retries in application policy.** If DBOS is used, classify steps: local deterministic processing may retry; paid-provider calls should have retries disabled unless explicitly authorized. Persist request/result/idempotency metadata and use strict response validation plus deterministic fallback. DBOS's at-least-once boundary means a crash around external side effects can still cause a repeated call absent application-level safeguards.
4. **Compose footprint:** One Varde app + SQLite is the simplest fit if lifecycle workflows are modest: a durable inbox/outbox/state machine can live in the same database and process. ntfy/Gotify add a separate service if chosen for push. DBOS adds orchestration machinery and its system database, even when containerized alongside Varde; this may move complexity rather than eliminate it.
5. **Separate recurring monitoring incidents from incoming alerts.** An incident monitor typically models an ongoing condition with open/resolve/repeat notifications; an incoming alert archive models individual immutable events. Do not substitute incident-state semantics for retained source alerts and generated-view history without an explicit domain mapping.

## Recommendation

For the stated single-user, read-only first release, start with **Varde-owned lifecycle and canonical SQLite storage**, using a small explicit state machine plus durable work/outbox records rather than adopting an alert platform as the inbox. Evaluate ntfy or Gotify only as replaceable delivery infrastructure after checking Android integration, authentication, and recovery behavior; ntfy offers clearer documented replay/cache controls, but its defaults and cache semantics do not meet indefinite archival needs. Gotify has MIT licensing and SQLite support, but retention/history guarantees appear less suitable from the reviewed docs.

Adopt DBOS only if the workflow graph, restart recovery, or operational visibility is materially more complex than a Varde-owned job/outbox mechanism. It can replace some durable execution plumbing, **not** Varde's alert lifecycle or data model. Before choosing, verify selected-version SQLite support/deployment, evaluate DBOS upgrades/backups, and test crash injection around provider calls to confirm retry policy. This recommendation is conditional and does not preempt unresolved product-contract decisions.
