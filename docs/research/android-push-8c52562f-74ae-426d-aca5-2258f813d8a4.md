# Android push delivery for a self-hosted homelab backend

**Research date:** 2025-03-08 (source pages are living documents; verify details before implementation).  
**Scope:** Wake a native Android app when its user's self-hosted backend receives an alert. Push is only a hint; the app fetches full alert data from that backend over a user-selected route (Pangolin, Tailscale, or public Internet). No implementation performed.

## Executive recommendation

For a first release, use **Firebase Cloud Messaging (FCM) data-only, high-priority messages** as a minimal wake-up signal, then fetch the alert from the user's backend. This is the Android path Google itself recommends for server-originated real-time messages under Doze; high priority gives FCM an opportunity to wake the device and temporary network access. Keep callback handling short and use WorkManager for work that cannot finish promptly. Display a user-visible alert promptly when appropriate: FCM can demote high-priority traffic when messages repeatedly do not result in user-facing notifications.

This choice introduces a Google/Firebase dependency and means each user's backend must securely send through FCM (with per-user registration data and trusted server credentials/configuration). Do not assume a user's homelab can reach the phone directly through their chosen private route: the phone is often asleep, behind NAT, or has no continuously available app connection. The user's chosen path is relevant to the **subsequent fetch**, not to FCM's push transport. A fetch can fail if that route is unavailable; treat push as best-effort and recover by fetching/synchronizing when the app next opens or scheduled work can run.

UnifiedPush is a credible **opt-in alternative** for users who want non-Google/self-hostable push infrastructure, but it requires a compatible installed distributor and push server, explicit Android integration/registration lifecycle, and a more fragmented setup. ntfy can act as a UnifiedPush distributor and can use a self-hosted ntfy server, but Android's background/power constraints still apply; the cited UnifiedPush spec describes distributor foreground treatment on message delivery rather than guaranteeing universal latency or delivery.

## Options compared

| Option | Background/wake characteristics | Requirements and fit | Main caveats |
|---|---|---|---|
| **FCM** | FCM is designed for idle/Doze delivery. Normal-priority messages may be deferred in Doze. High priority attempts immediate delivery, can wake a sleeping device, and grants limited processing/network access. | Native Android FCM SDK; Firebase project/app registration; backend sends via Admin SDK or HTTP v1 API; app instance token/FID associated with user's backend. Strongest first-release fit for general Android devices with Google services. | Depends on Google services/connectivity and Firebase; not a hard real-time or guaranteed-delivery SLA in the cited docs. Tokens/credentials are secrets; backend setup and registration lifecycle required. High-priority abuse/non-visible messages may be deprioritized. |
| **UnifiedPush** | Android distributor receives the push and forwards to app. The Android spec says distributor MUST raise app to foreground importance for 5 seconds when forwarding. | App integrates UnifiedPush connector/spec; user installs/selects compatible distributor. ### FCM behavior and reliability limits

- Google's Android Doze guidance says device idle restricts network access and defers jobs, syncs, and standard alarms. It specifically recommends FCM instead of a persistent connection for real-time messages. FCM high-priority messages can wake the app and provide temporary network access and partial wakelocks; normal priority may wait for a maintenance window or until the user wakes the device. [Android Doze and App Standby](https://developer.android.com/training/monitoring-device-state/doze-standby)
- FCM documents normal priority as the default; it can be delayed in Doze. High priority attempts immediate delivery and permits limited processing/network access. It is meant for time-sensitive, user-visible content. [FCM Android message priority](https://firebase.google.com/docs/cloud-messaging/android-message-priority)
- FCM calls `FirebaseMessagingService.onMessageReceived()` for data-only messages in background; notification payloads instead go to the system tray, and combined notification+data messages put data in the launch intent when backgrounded. The callback has a short window; avoid slow server fetches there and schedule longer work via WorkManager. [FCM receive messages on Android](https://firebase.google.com/docs/cloud-messaging/android/receive-messages)
- FCM warns that messages may be lost in circumstances such as more than 100 pending messages for an app instance or a device not connecting to FCM for over a month; `onDeletedMessages()` is the signal for a full sync. This supports treating push as a hint rather than the authoritative alert store. [FCM receive messages](https://firebase.google.com/docs/cloud-messaging/android/receive-messages)
- **Inference:** A minimal signal followed by backend fetch trades immediate notification richness for reduced exposure to third-party push infrastructure; the app must have a viable backend route at fetch time. The FCM priority guidance cautions against doing an additional network request before rendering a high-priority notification because latency can make notification processing miss its window. Therefore, if alerting immediately matters, either render a generic “new alert” notification from the signal then fetch/update it, or include only carefully chosen user-visible minimal text in push. This differs from the strict “signal only, fetch before notifying” design and requires a product choice.

### UnifiedPush behavior and requirements

- UnifiedPush defines the connector/distributor registration flow: app asks distributor to register, receives an endpoint, and sends it to its application server; push server delivers to distributor which forwards a byte payload to app. The distributor may retry unacknowledged messages. Endpoint URLs are capability URLs and must contain sufficient random entropy; payloads are encrypted Web Push content (RFC 8291), 1–4096 bytes. [UnifiedPush Android specification](https://unifiedpush.org/developers/spec/android/)
- The spec requires a distributor to raise the receiving app to foreground importance for five seconds when delivering a message. Its example implementations include privileged temporary allowlisting or binding to the app's foreground-importance service. This is a protocol requirement, **not evidence of guaranteed end-to-end delivery or latency**. [UnifiedPush Android specification](https://unifiedpush.org/developers/spec/android/)
- UnifiedPush's ntfy setup documentation says install ntfy Android, grant permissions (including notification and battery optimization exemptions as needed), optionally configure a self-hosted server, then select ntfy as distributor in a UnifiedPush-capable app. [UnifiedPush ntfy distributor guide](https://unifiedpush.org/users/distributors/ntfy/)
- **Inference:** Supporting UnifiedPush inside this app does not automatically give every user self-hosted push; a compatible Android distributor must exist on the device and be configured. It is better treated as an advanced/opt-in integration unless the product is committed to supporting distributor discovery, diagnostics, changing endpoints, and setup support.

## Security and privacy

### FCM

- The FCM service environment requires secure storage for server authorization credentials and registration identifiers; Firebase says registration tokens must be kept secret. The server sends to Google's FCM backend, which routes to the app. [FCM server environment](https://firebase.google.com/docs/cloud-messaging/server-environment)
- Limit the message to an opaque event marker/version and no alert content, hostnames, or secrets. This limits content exposure to the push provider, although Google still handles routing metadata and delivery. **Inference:** Whether an opaque marker is personal data depends on its identifiers and deployment context; avoid stable user-identifying data in it.
- Never embed FCM service-account credentials in the Android APK. Firebase identifies FCM sending as a trusted server operation and recommends its Admin SDK or HTTP v1 API. [FCM server environment](https://firebase.google.com/docs/cloud-messaging/server-environment)
- One backend per user implies each backend needs access to trusted FCM send authorization. Giving every homelab a service-account private key is operationally and security sensitive. Options include user-managed project credentials or a centralized relay service, but the latter changes the trust/data architecture and requires separate product/security design. **This is an architectural implication, not Firebase's prescribed deployment for this particular product.**

### UnifiedPush

- The spec's endpoint is a secret-like capability URL protected by sufficient entropy; push content must be encrypted as defined by RFC 8291. App server authentication may require VAPID. Treat endpoint, VAPID private key, and registration token as credentials; do not log or expose them. [UnifiedPush Android specification](https://unifiedpush.org/developers/spec/android/)
- Self-hosting ntfy can reduce reliance on a shared public ntfy service, but the Android distributor and network path remain part of the trust and availability boundary. ntfy's guide notes unauthenticated-by-default server use and recommends access controls when restricting server resources. [ntfy UnifiedPush guide](https://unifiedpush.org/users/distributors/ntfy/)

### Notification permission

Android 13+ requires runtime `POST_NOTIFICATIONS` permission for ordinary non-exempt notifications; new installs have notifications off until permission is granted. If denied, the app generally cannot post notifications. Prompt in context and provide an understandable recovery path. [Android notification runtime permission](https://developer.android.com/develop/ui/compose/notifications/notification-permission)

## Homelab reachability and chosen routes

- FCM/UnifiedPush transports the **wake signal** through its own push infrastructure. Once awoken, the app uses the user's configured backend URL/route for authenticated retrieval. It should not assume the backend-to-phone connection is directly reachable.
- Pangolin, Tailscale, and public Internet are not interchangeable push mechanisms. They are candidate app-to-backend fetch paths. **Inference:** Tailscale fetch requires the phone's Tailscale connectivity and backend reachability; a public endpoint requires appropriate exposure/TLS/authentication; a Pangolin route depends on its configuration and availability. Push arrival cannot establish that the route is live. Make fetch retryable and surface stale/unreachable backend state.
- Best-effort robustness: persist server-side alerts with monotonic cursor/sequence; signal “new data exists”; fetch since last cursor on wake and on app foreground. If push drops, next foreground sync repairs state. Avoid relying on a one-message-per-alert contract.

## First-release recommendation and decision points

1. **Implement FCM data-only wake hints**, with high priority only when a real user-facing alert is pending; include an opaque event/cursor hint, not alert content. On receipt, render a generic or minimal notification immediately if product requirements demand prompt user visibility, and fetch details from the configured backend using short bounded work; otherwise schedule fetch work and accept that display can be delayed. Deduplicate by event/cursor.
2. Register/update the device's FCM identifier with the user's authenticated backend, associate it with that user/device, support token/FID rotation and removal, and delete invalid registrations based on send errors. Firebase recommends tracking freshness and removing invalid/stale registrations. [FCM token management](https://firebase.google.com/docs/cloud-messaging/manage-tokens)
3. Keep all FCM send credentials in a trusted server environment; define secure provisioning and rotation for the one-backend-per-user model before shipping. Admin SDK is Firebase's recommended interaction; HTTP v1 is also supported. [FCM server environment](https://firebase.google.com/docs/cloud-messaging/server-environment)
4. Handle notification permission denial, FCM unavailable/offline cases, route failures, and missed pushes. Perform a full reconciliation on app foreground and after FCM deleted-message indication. Do not use exact alarms or battery-optimization exemptions as a substitute for push; Android recommends FCM for this use case. [Android Doze guidance](https://developer.android.com/training/monitoring-device-state/doze-standby)
5. Consider UnifiedPush later as an opt-in for users who explicitly prefer a configurable/self-hosted distributor path and accept setup complexity. Validate actual distributor/device coverage and message delivery behavior before promising reliability.

**Open product/security decision:** Does “push payload should contain only a minimal signal, then app fetches alert” require the app to fetch before it shows any notification? Google recommends immediate rendering and warns that server fetch before notification can be risky on high-latency networks. If fetching is mandatory first, the design accepts possible delayed/missed user-visible alerts, and high-priority FCM eligibility may be affected if messages do not produce visible notifications.

## Source ownership and confidence

Claims above are grounded in first-party Android Developers, Firebase Cloud Messaging, and UnifiedPush specification/project documentation. These establish documented mechanics and recommendations, not an end-to-end delivery guarantee for this exact homelab topology. No primary source examined makes a universal latency or delivery guarantee across OEM battery policies, network conditions, user settings, or provider outages. “Reliable” here means the platform-supported best fit for prompt background wake, paired with reconciliation—not guaranteed delivery.
